# 0001. Миграции схемы: SQL-файлы и свой раннер

Дата: 2026-11-06. Статус: принято.

## Контекст

Таблиц в проекте будет пять (jobs, documents, chunks, llm_calls, schema_migrations), с индексами pgvector
(hnsw под косинусную метрику), генерируемыми колонками (tsvector) и запросами с оконными функциями.
Варианты: Doctrine Migrations (миграции на PHP-классах) или обычные SQL-файлы, которые применяет раннер.

## Решение

SQL-файлы в `db/migrations/NNNN_название.sql` и раннер `App\Core\Migrate` (команда `app:migrate`).
Раннер применяет файлы по порядку имён, каждый в своей транзакции, и записывает версию в таблицу
`schema_migrations`. Повторный запуск ничего не применяет.

## Почему

- Всё, что дальше нужно схеме, пишется на SQL: `CREATE EXTENSION vector`, `vector(384)`, `USING hnsw`,
  `GENERATED ALWAYS AS (to_tsvector(...)) STORED`. Прослойка, которая прячет SQL, будет мешать, а не помогать.
- Файл миграции читается наставником как есть, без знания API Doctrine Migrations.
- Раннер — тридцать строк, его поведение полностью покрыто тестом `tests/Core/MigrateTest.php`.

## Последствия

- Откат миграций не поддерживается: правка схемы — новый файл вперёд. Для учебного проекта достаточно.
- Порядок задаёт числовой префикс имени; два файла с одним префиксом недопустимы.
