# 0001. Миграции схемы: SQL-файлы и свой раннер

Дата: 2026-11-09. Статус: принято.

## Контекст

Таблиц пять: `schema_migrations`, `jobs`, `documents`, `chunks`, `llm_calls`. Нужны индекс pgvector
(hnsw под косинусную метрику), генерируемая колонка `tsvector` и запросы с оконными функциями.
Варианты: Alembic или обычные SQL-файлы с простым раннером.

## Решение

SQL-файлы `db/migrations/NNNN_название.sql` и раннер `app/core/migrate.py` (`make migrate`).
Раннер применяет файлы по порядку имён, каждый в своей транзакции, и записывает версию в
`schema_migrations`. Таблицу версий создаёт сама первая миграция вместе с `CREATE EXTENSION vector`.
Повторный запуск печатает «Новых миграций нет».

## Почему

- Всё нужное схеме пишется на SQL: `vector(384)`, `USING hnsw (embedding vector_cosine_ops)`,
  `GENERATED ALWAYS AS (to_tsvector(...)) STORED`. Прослойка, которая прячет SQL, тут мешает.
- ORM в проекте нет, поэтому автогенерация миграций Alembic ничего не даёт.
- Файл миграции читается как есть; раннер — около 40 строк, покрыт тестом.

## Последствия

- Отката нет: правка схемы — новый файл вперёд.
- Два файла с одним числовым префиксом раннер отклоняет.
